## Findings

### 1. Schema — columns returned

**Source:** https://alpaca.markets/sdks/python/api_reference/data/models.html + R1 research

Bar model fields (confirmed):
- `timestamp` — UTC, bar open time (see §2 below)
- `open`, `high`, `low`, `close` — float, raw trade price
- `volume` — total shares traded during bar window
- `trade_count` — number of qualifying trades
- `vwap` — volume-weighted average price

When using `alpaca-py` SDK with `bars.df`, the DataFrame is multi-indexed by `(symbol, timestamp)` when requesting multiple symbols. For single-symbol pull (`["SPY"]`), drop the symbol level or use `bars.df.loc["SPY"]`.

**Not present in bar response:** bid/ask, spread, tape letter (those are in Quote/Trade models).

### 2. Timestamp semantics

**Source:** https://forum.alpaca.markets/t/alpaca-historical-data-bar-timestamp/15867 (Alpaca staff correction)

- Timestamps are **UTC**.
- Timestamp = **bar open time** (left edge of interval). A bar labelled `2020-03-16 13:30:00+00:00` covers the minute range 13:30–14:30 UTC, which is 09:30–10:30 ET (winter, EST = UTC-5).
- Alpaca's own documentation initially stated "bar close time" — this was confirmed as a documentation error by an Alpaca staff member. Use bar-open semantics.

**DST implication:** UTC timestamps are unambiguous across DST transitions. In winter (EST, UTC-5), RTH 09:30–16:00 ET = UTC 14:30–21:00. In summer (EDT, UTC-4), RTH 09:30–16:00 ET = UTC 13:30–20:00. A rolling window built on UTC timestamps will have a 1-hour shift in the UTC equivalent of "session open" across DST boundaries. Filter by converting to `America/New_York` tz before applying `.between_time()`.

### 3. Trading-hour handling — the 09:00 vs 09:30 bar problem

**Source:** https://forum.alpaca.markets/t/get-bars-for-opening-hours-only-and-following-market-timing/7750 (Alpaca staff) + GitHub issue #552

Critical finding: **Alpaca H1 bars are clock-hour aligned, not market-session aligned.**

- H1 bars aggregate all minute bars within each clock hour.
- Pre-market starts at 04:00 ET. The first clock-hour bar containing RTH trades is therefore the **09:00–10:00 ET bar** (14:00–15:00 UTC winter). This bar contains 30 minutes of pre-market data (09:00–09:30 ET) mixed with the first 30 minutes of RTH (09:30–10:00 ET).
- There is NO native 09:30-aligned hourly bar from Alpaca's H1 endpoint.
- The last RTH bar (15:00–16:00 ET) is a clean 60-minute bar. Post-market starts at 16:00 ET so it does not contaminate the 15:xx bar.
- Alpaca staff recommendation (forum): fetch minute bars and resample with pandas `resample('1H', closed='left', label='left').agg({'open':'first','high':'max','low':'min','close':'last','volume':'sum'})` then `.between_time('09:30','15:59')` after converting to ET.

**Plan implication:** The `download.py` module must use minute bars + resample, NOT `TimeFrame.Hour` directly, if clean 09:30-session-aligned bars are required. If using `TimeFrame.Hour` directly, the 09:00 bar must be dropped (it is a mixed pre-market + RTH bar) and the session starts at 10:00 (losing the 09:30–10:00 open candle entirely).

**Recommended approach:** Minute resample. Produces correct 09:30–10:30, 10:30–11:30, ..., 15:30–16:00 bars. 6.5 RTH bars per standard day (last bar is 30 min, not 60 min). This is the canonical approach.

### 4. Extended-hours bars

**Source:** GitHub issue #552 + forum thread 7750

- Alpaca H1 pull includes **pre-market (04:00–09:30 ET) and post-market (16:00–20:00 ET) bars** in addition to RTH bars.
- No native API parameter to exclude them.
- Must filter client-side after converting timestamps to `America/New_York`.
- For SPY specifically: extended-hours bars during pre/post will have real volume (SPY is actively traded in AH). They are not zero-volume — they cannot be dropped by volume filter alone. Only timestamp-based RTH filter works.

### 5. Holidays, weekends, half-days

**Source:** https://forum.alpaca.markets/t/historical-bar-data-missing-data/15032 (Alpaca staff: "No valid trades, no bar") + NYSE calendar data

**Holidays and weekends:** No bar returned. Gap in the timestamp series. Standard cleaning = assert no bar is present for known exchange holidays. Library `exchange_calendars` (formerly `trading_calendars`) provides authoritative NYSE session list — use it to validate expected vs actual trading days.

**Half-days (early closes at 13:00 ET):** Recurring half-days in project window:
- Day after Thanksgiving: every year 2018–2025, closes 13:00 ET
- Christmas Eve: 2018, 2019, 2020, 2024 (when Dec 24 falls on weekday), closes 13:00 ET

On half-days: Alpaca returns bars only for the active period. For minute-resampled approach, session ends at 13:00 ET — the last bar is 12:30–13:00 (30 min) rather than 15:30–16:00. No special flag is added; the day simply has fewer bars (7 bars for 09:30–13:00 vs 13 for full day).

**Cleaning rule for half-days:** Do NOT drop them. They are real trading sessions. Flag them with a `session_type` column (`'full'`, `'half'`) using the `exchange_calendars` session schedule. SMC indicators computed across sessions should skip or weight these differently.

### 6. Zero-volume bars

**Source:** Alpaca staff quote: "Bars are only created if there are 'valid' trades during the bar. No valid trades, no bar."

**For SPY specifically:** Zero-volume RTH bars are effectively impossible. SPY is the most liquid ETF in the world — millions of shares trade every minute during RTH. The plan's "remove zero-volume candles" rule is appropriate as a defensive sanity check but will never trigger for SPY RTH bars.

**If zero-volume RTH bar appears for SPY:** Treat as data corruption, not sparse trading. Drop the bar and flag it. Do not interpolate — an SPY RTH zero-volume bar means no qualifying trades passed the SIP condition filter, which indicates a data feed issue.

**Extended hours:** AH bars can legitimately have lower volume. This is another reason to filter by RTH timestamps rather than by volume.

### 7. OHLC integrity check

**Source:** https://forum.alpaca.markets/t/incorrect-spikes-peaks-in-historical-data/10236 (Alpaca staff on root cause)

Known Alpaca data quality issue: **OHLC spikes from late-reported out-of-sequence trades and derivatively-priced trades.** Alpaca has patched many of these in historical data, but some remain.

Integrity invariants that must hold for any valid OHLC bar:
1. `low <= min(open, close)` — low must be at or below both open and close
2. `high >= max(open, close)` — high must be at or above both open and close
3. `low <= high`
4. All OHLC values > 0
5. `volume > 0` (for RTH SPY)

Any bar violating (1) or (2) is definitionally corrupt. Root cause is a single anomalous print setting the high or low outside the open/close range without affecting the close. These should be dropped, not repaired — the close price is the most reliable field.

**COVID March 2020:** High volatility in this window (SPY dropped ~34% peak-to-trough). The candles are extreme but should be legitimate. Alpaca historical bars for 2020 are SIP-consolidated and have been through their data cleaning pipeline. No evidence of systematic corruption for major ETFs in this window was found in research. The OHLC integrity check above will catch any corrupt bars regardless.

### 8. DST transitions

**Source:** Standard UTC handling confirmed by Alpaca staff (forum thread 11537)

- Alpaca returns UTC timestamps universally. DST is not Alpaca's problem — it is the pipeline's responsibility.
- US DST transitions (2018–2026): 2nd Sunday March → 1st Sunday November. Each transition shifts the UTC equivalent of "09:30 ET" by 1 hour.
- DST does NOT create 23-hour or 25-hour trading days for NYSE. NYSE always opens at 09:30 ET and closes at 16:00 ET local time, regardless of DST. The UTC equivalent changes by 1 hour.
- **Practical risk:** A rolling-window statistic computed on UTC timestamps without tz-conversion will have a 1-hour misalignment on DST transition days when comparing "yesterday's close bar" to "today's open bar." This affects first-bar detection in session-level logic.
- **Mitigation:** Convert all timestamps to `America/New_York` (pytz or zoneinfo) before any session-boundary logic. Use `.dt.tz_convert('America/New_York')` on the DataFrame index.

## Recommendation

**Use minute-bar resample approach, not `TimeFrame.Hour` directly.**

Rationale: Clock-hour H1 bars from Alpaca produce a contaminated 09:00–10:00 bar mixing pre-market and RTH data. The only way to get correct 09:30-anchored sessions is minute resample + `.between_time()`. The extra API cost (pulling 1-min bars vs 1-hour bars) is negligible for a one-time historical pull.

`download.py` interface contract:
1. Pull SPY 1-min bars from Alpaca (`TimeFrame.Minute`, `adjustment="raw"`).
2. Convert index to `America/New_York`.
3. Filter to RTH: `.between_time('09:30', '15:59')` (inclusive, covers last partial bar at 15:30).
4. Resample to H1: `resample('1H', closed='left', label='left').agg(...)`.
5. Drop any bar with `volume == 0` (SPY invariant check).
6. Run OHLC integrity check: drop bars where `low > min(open, close)` or `high < max(open, close)`.
7. Tag session type using `exchange_calendars` NYSE schedule.

## What /nb:plan needs to know

- `TimeFrame.Hour` from Alpaca produces clock-aligned bars — first bar is 09:00-10:00 ET, not 09:30-10:00 ET. **Plan must specify minute resample approach.**
- Alpaca returns UTC timestamps. All session-boundary logic must convert to `America/New_York` first.
- Bar timestamp = bar open time (left edge). A bar timestamped `14:30 UTC` covers 14:30–15:30 UTC = 09:30–10:30 ET (winter).
- Extended-hours bars are included in any Alpaca bar pull; RTH filter is mandatory, not optional.
- `exchange_calendars` library (pip install exchange-calendars) provides NYSE trading calendar 2018–2026 including half-day sessions. Use it to validate trading day count and tag session type.
- Half-days: 2 per year average (Black Friday + Christmas Eve when applicable). Expect ~16 half-days across the 2018–2026 window. Plan must not treat these as corrupt data.
- OHLC integrity check is mandatory — known Alpaca data quality issue with spike prints from late/out-of-sequence trades.
- Minute-bar API pull for 8.3 years of SPY is large. Rate limit: 200 req/min. Alpaca paginates automatically via SDK. Monitor for pagination timeout.
