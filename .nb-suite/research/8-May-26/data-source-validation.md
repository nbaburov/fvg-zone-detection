## Project context

Greenfield project. No data pipeline yet. Target: SPY H1 OHLCV 2018-01-01 to 2026-05-08 (~8.3 years, ~13,595 trading candles). Labels will be generated by the `smart-money-concepts` library using FVG detection. Raw (unadjusted) prices required — SMC structure is defined by literal price levels, not dividend-corrected ones. Adjustment shifts OHLC values backward in time, distorting gap geometry.

## Findings

### yfinance (primary assumption — FAILED empirical test)

**Source:** Live call `yf.download('SPY', start='2018-01-01', end='2026-05-08', interval='1h', auto_adjust=False)` + official yfinance docs at https://ranaroussi.github.io/yfinance/reference/api/yfinance.download.html
**Mechanism:** Unofficial scraper of Yahoo Finance web endpoints. Not an official API. Returns DataFrames from Yahoo's query API.
**Fit:** No. Hard limit confirmed.
**Empirical result:**
```
Yahoo error = "1h data not available for startTime=1514782800 and endTime=1778212800.
The requested range must be within the last 730 days."
Rows returned: 0
```
**What that means:** As of 2026-05-08, the cutoff is approximately 2024-05-08. Any `start` date earlier than that returns zero rows for H1 interval. Target of 2018-01-01 is 6.35 years outside the window.
**Candles available vs needed:** ~3,389 vs ~13,595. A chunked-request workaround cannot overcome a server-side date cap — Yahoo simply does not store H1 data older than 730 days.
**auto_adjust default:** `True` — yfinance v1.3.0 adjusts OHLC for splits and dividends by default. Must explicitly pass `auto_adjust=False` to get raw prices. With `auto_adjust=True`, the `Adj Close` column is dropped and all OHLC values are shifted. This distorts historical FVG geometry.
**Reliability risk:** Yahoo changed their API in February 2025 and broke all yfinance versions; same-day patch was released. Yahoo makes undocumented endpoint changes with no notice. Rate limits: 429 errors under rapid fetching. No SLA.
**Version tested:** 1.3.0

### Chunked yfinance workaround (attempt to rescue primary source)

**Source:** GitHub issue discussions, community workarounds
**Mechanism:** Split the date range into 730-day chunks, fetch each, concatenate. Still uses yfinance.
**Fit:** No. The 730-day cap is enforced by Yahoo's backend on the server side — it is not a yfinance library limit. Chunked requests for dates before the 730-day window return empty DataFrames. This is confirmed by the error message explicitly referencing `startTime` validation on Yahoo's API. The workaround is not viable.
**Risk:** Wasted implementation effort + false confidence in approach.

### Alpaca Markets — free tier (recommended alternative)

**Source:** https://docs.alpaca.markets/docs/about-market-data-api
**Mechanism:** Official REST API and Python SDK (`alpaca-py`). Free plan uses IEX exchange feed for real-time; historical bars use SIP-consolidated data. Historical equity bars available since 2016-01-01. Rate limit: 200 API calls/minute on free plan.
**Fit:** Yes — with one caveat on IEX vs SIP distinction (see below).
**History depth:** Since 2016. Covers 2018-01-01 start with 2 years of margin. Full 8.3-year target achievable.
**Timeframe support:** Hourly bars (`TimeFrame.Hour`) natively supported.
**Adjustment:** Alpaca returns raw trade prices. No dividend/split adjustment applied to OHLCV bars by default. Raw prices suitable for SMC structure detection.
**Free plan real-time restriction:** IEX feed only for real-time quotes (15-min delay). Historical bar data is SIP-consolidated and not restricted to IEX-only. This distinction matters for live inference but NOT for historical data retrieval for this project.
**Install:** `pip install alpaca-py`. Requires free account signup for API key (paper trading account sufficient — no real money required).
**Risk:** Requires account creation. IEX vs SIP data quality for historical bars needs verification at data understanding phase. Rate limit at 200 calls/min is generous for a one-time bulk download but must be handled if chunking large requests.

**Exact call (primary):**
```python
from alpaca.data.historical import StockHistoricalDataClient
from alpaca.data.requests import StockBarsRequest
from alpaca.data.timeframe import TimeFrame
from datetime import datetime

client = StockHistoricalDataClient(api_key=API_KEY, secret_key=API_SECRET)
request = StockBarsRequest(
    symbol_or_symbols=["SPY"],
    timeframe=TimeFrame.Hour,
    start=datetime(2018, 1, 1),
    end=datetime(2026, 5, 8),
    adjustment="raw"   # explicitly raw — no split/dividend adjustment
)
bars = client.get_stock_bars(request)
df = bars.df
```

The `adjustment="raw"` parameter is the correct flag. Alternatives are `"split"`, `"dividend"`, `"all"`. Use `"raw"` only.

## Recommendation

**Primary source: Alpaca Markets free tier.**

Use `alpaca-py` SDK. Pull SPY H1 bars from 2018-01-01 to present with `adjustment="raw"`. Free account (paper trading signup) is sufficient. No cost. History depth confirmed since 2016. SDK is official and actively maintained.

**Fallback (if Alpaca signup is blocked or API breaks during Phase 3):** Stitch yfinance from the 730-day window (back to May 2024) to cover the most recent data only, combined with a pre-cached Parquet file from an alternative source for 2018–2024. This is not recommended as primary because it creates two-source stitching complexity with different adjustment semantics.

**Do NOT use yfinance as primary for H1 history.** The 730-day cap is a hard server-side constraint, confirmed empirically. Chunking workarounds do not circumvent it.

**Adjustment rule:** Always pass `adjustment="raw"` (Alpaca) or `auto_adjust=False` (yfinance). SMC FVG geometry depends on absolute price levels. Any adjustment that shifts OHLC values distorts historical gap positions.
